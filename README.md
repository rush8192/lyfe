The `vision` folder contains charter documents outlining the vision for the key systems we want to implement. It contains most of the `what` for the scope of the project. If any part of the vision proves impossible to implement, or we make an implementation decision that contradicts the vision, we should note that choice in the relevant vision file.

The `plan` folder contains more fleshed-out implementation plans for how to execute the vision. These plans should sketch out a more concrete and detailed version of the vision that maps to the technology stack we will use. The correct level of detail is pseudocode, system diagrams, and any other artifacts that help record key implementation decisions. Plans should be kept up to date as we dive deeper into implementation, but ultimately flow downstream from the vision. We may have multiple child directories in this folder, one for each version of the implementation we attempt. We will start with `v1`.

The `implementation` folder contains actual source files and all relevant scaffolding for a concrete implementation of the project. All source files, assets, and related materials will live in a child directory that corresponds to a directory in the `plan` folder, starting with `v1`.

For v1, [`implementation/v1/BACKLOG.md`](implementation/v1/BACKLOG.md) is the living source of truth for implementation status, dependency order, and acceptance criteria. Stage A's deterministic end-to-end walking skeleton is complete; `WORLD-200` is the next ready Stage B slice. The server can run natively for development or through the portable Docker Compose path documented in [`plan/v1/DEPLOYMENT_AND_PORTABILITY.md`](plan/v1/DEPLOYMENT_AND_PORTABILITY.md).
